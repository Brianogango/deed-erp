# Repair Workflow Implementation Notes

The requested workflow can be implemented safely in the existing store-driven repair module without altering the `users` or `employees` database tables, records, relations, or API routes. The repository already contains a comprehensive repair flow in `lib/store.tsx`, customer approval synchronization in `app/api/portal/repair/[ref]/approve/route.ts`, and public tracking pages under `/portal/repair`.

The implementation will focus on the remaining workflow gaps visible in the current codebase. First, the staff workflow should explicitly support `pending_verification` as the intake queue and provide a verification action that changes a job to `received` after the physical device and accessories are confirmed. Second, the UI permission logic for quote generation should match the store rule by restricting creation and modification to `technical_lead`, `director`, or the assigned technician, not sales or finance roles. Third, automatic procurement requests created during customer quote approval should use a durable status of `pending`, include a repair reference, and notify inventory-oriented roles rather than only technical leads. Fourth, manual status updates should also sync the portal projection and append communication records so customer-facing updates remain consistent. Fifth, public self-service intake should be added at `/portal/intake` with mandatory liability waiver acceptance for direct repairs and should write to the repair store only, not to user or employee data.

No Prisma migration against `users` or `employees` will be created. If any schema/type enhancement is necessary, it will be limited to repair-related TypeScript/store structures or non-destructive repair fields already persisted as JSON in `app_state`.
